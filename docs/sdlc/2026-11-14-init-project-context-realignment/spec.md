# Spec: Réaligner init-project-context avec le kit (from intent.md 2026-11-14)

Status: accepted · Reviewed by: Hachem LATRACH · Date: 2026-11-14 · Versioned: this file is the contract reviewers read in the merge request (MR)

Cérémonie héritée de l'intent : **full** (contrats partagés : sens de `REVIEW.md`, règle de `code-review`, forme de l'`AGENTS.md` que les commandes lisent).

## Objective
Que la skill `init-project-context` produise exactement ce que les commandes et les skills du kit lisent dans un projet (y compris un monorepo), sans recopier le kit ni affaiblir la revue, et que des tests empêchent une nouvelle dérive.

## Scope and non-goals
- In : la skill `init-project-context` et ses modèles (`AGENTS.md`, `REVIEW.md`, `plan.md`, `intent.md`) ; la règle de `code-review` sur `REVIEW.md` ; `setup-workflow` (où il écrit) ; la proposition de la skill par `/review` et par `tdd` ; `commands/spec.md` (init-workflow) ; le contexte du kit et le bloc Claude Code sur `CLAUDE.md` ; docs, ADR 0032, CHANGELOG ; tests de contrat ; deux cas d'eval.
- Out : écrire dans un vrai projet (`leezy-portal` viendra après, avec la skill réalignée) ; la matrice des CLI face au remplacement de Gemini CLI par agy ; un outil qui détecte la structure d'un monorepo par script (la skill lit et propose, le modèle juge) ; `GLOSSARY-MAP.md` créé par la skill (elle le lit seulement).

## Requirements
Chaque exigence a un critère d'acceptation vérifiable. « Test » = un test de la suite du kit (`python3 -m unittest`), sans modèle.

1. **`REVIEW.md` ajoute, ne retire jamais (décision A).** Le modèle commence par : les passes du kit (Bugs, Security, Domain, Standards, Compliance, Tests) s'appliquent toujours ; ce fichier y **ajoute** ce qui est propre au projet ; il n'en retire aucune. Il garde des sections pour ces ajouts : lignes du Domain, conventions du Standards, ce que veut dire Important ici, plafond des nits, ce qu'on ne signale pas. La section « Full mode » disparaît (elle répète `/review` et le doubter). — Acceptance : un test vérifie que chaque passe nommée dans `code-review` (ses puces en gras) figure dans le modèle, que « Run four passes » et « Full mode » n'y sont plus, et que la phrase « never removes » y est.
2. **`code-review` : `REVIEW.md` ajoute.** La puce Standards remplace « (its passes, severity rule, nit cap and exclusions win) » par une règle : ce que `REVIEW.md` ajoute s'applique (lignes de domaine, règle de gravité, plafond, exclusions) ; il ne retire jamais les passes Tests, Security ni Standards ; une demande de retrait est signalée dans les limites de la revue. Une skill de projet nommée `code-review` reste la seule façon de remplacer la revue (inchangé). — Acceptance : test sur le texte (« win » absent de la puce Standards, « never removes » présent) ; version de la skill incrémentée.
3. **Modèle `plan.md` à jour.** En-tête `Ceremony: quick | standard | full` ; sections dans l'ordre Risks, Files that change, Order of work, Proof. — Acceptance : test sur le vocabulaire et l'ordre des titres ; aucun des mots « tweak », « small feature », « large or fuzzy » dans les modèles ni dans les commandes.
4. **Modèle `intent.md` avec Risks.** Une section `## Risks` après Constraints, marquée « full level: production data, irreversible operations, personal data; how a failure would show and how to undo it; delete below full ». — Acceptance : test sur la présence et la position du titre.
5. **Pas de `CLAUDE.md` par défaut (décision B).** La skill ne propose plus de créer `CLAUDE.md`. Quand le dépôt en a déjà un qui n'importe pas `AGENTS.md`, elle propose d'ajouter `@AGENTS.md` en tête. Le contexte du kit (ligne `CLAUDE.md` de `templates/kit-context.md`) et le bloc généré par `installer/adapters/claude.py` disent la même chose, sans grossir. `setup-workflow` écrit son bloc dans `AGENTS.md`, jamais dans `CLAUDE.md`. `docs/cli/claude-code.md` cite la doc officielle (lecture native d'`AGENTS.md` sans `CLAUDE.md`, v2.1.277+, réglage « Project instructions »). — Acceptance : tests : la skill ne contient plus « only when the repo is used with Claude Code… one line » mais l'ajout en tête ; `setup-workflow` ne dit plus d'éditer `CLAUDE.md` ; contexte du kit sous 3 800 caractères ; bloc Claude Code régénéré et cohérent (test existant de l'adaptateur adapté).
6. **Monorepo : carte à étages, montrée avant d'écrire.** Quand le dépôt a plusieurs apps, la skill lit `references/monorepo.md` (chargé seulement dans ce cas). Indices, du plus fiable au moins fiable : fichiers de workspace (`pnpm-workspace.yaml`, `workspaces` de `package.json`, `nx.json`, `turbo.json`, `go.work`, `settings.gradle`, `pom.xml` à modules, `build.sbt` multi-projets), dossiers avec leur propre fichier de build, CI filtrée par dossier, `CODEOWNERS`. Elle propose : un `AGENTS.md` racine qui n'est que la carte (dossier → rôle → fichier à lire) ; un `AGENTS.md` par famille pour ce qui est commun ; un `AGENTS.md` d'app seulement si l'app diffère. Elle montre la carte (familles, apps, fichiers proposés, pourquoi) dans la proposition groupée et attend la correction ; indices absents ou contradictoires : elle demande. Ajouter plus tard le fichier d'une seule app est prévu (« initialise le contexte de `apis/billing` ») sans toucher aux autres. — Acceptance : test sur le texte (indices, trois étages, « only when it differs », carte avant écriture) ; cas d'eval monorepo (exigence 13).
7. **Héritage explicite.** Le fichier d'une famille ou d'une app commence, sous son titre, par une ligne de la forme : `Extends ../AGENTS.md. Overrides: <rule of the parent> → <rule here>.` (ou `Overrides: none.`). Il ne contient que ses différences. — Acceptance : test sur la forme dans `references/monorepo.md` ; cas d'eval monorepo.
8. **Règles `.gitignore` valables partout.** Lignes proposées : `**/docs/sdlc/**/intent.md`, `**/docs/sdlc/**/plan.md`, `**/docs/sdlc/handoff-*.md`. Vérifié à la main le 2026-11-14 : `docs/sdlc/**/intent.md` n'ignore pas `apis/billing/docs/sdlc/a/intent.md`, `**/docs/sdlc/**/intent.md` ignore les deux. Le contexte du kit (ligne Artifacts) et `/handoff` restent cohérents. — Acceptance : test qui extrait les lignes de la skill, les écrit dans un dépôt git temporaire et vérifie avec `git check-ignore` une note à la racine et une note de zone ignorées, un `spec.md` non ignoré.
9. **`AGENTS.md` allégé et complété.** Retirés du modèle : la ligne Artifacts (convention `docs/sdlc/`, « Never commit without being asked »), la phrase « never weaken, skip or delete a test » de l'étape 3 (déjà dans le contexte du kit), la section Commands Test et Lint qui répète le tableau. Ajoutés : une ligne « Versions » (langage, framework, outils de build) ; des lignes PHP (Composer, PHPUnit), Go, Scala (sbt), Java (Gradle) au tableau « Verifying your work » ; `composer.json`, `build.sbt`, `build.gradle(.kts)` dans les fichiers de stack lus. Gardés intacts : titres « Verifying your work » (colonnes Changed et Full), « ## Report », « Things the agent gets wrong » (forme `rule (since YYYY-MM: …)`), « Where the rest lives ». — Acceptance : tests : les titres lus par les commandes sont présents ; « Never commit », « never weaken » et `docs/sdlc/` absents du modèle ; les lignes de stack présentes.
10. **Nettoyage.** Description de la skill : plus de « docs/ folder ready » ; elle nomme `AGENTS.md`, `REVIEW.md`, `GLOSSARY.md`, la règle git et le monorepo. `aikit-summary` et `docs/commands.md` : une confirmation groupée (plus « per file »). Métadonnées `aikit-optional-*` : gardées (écart décidé au build : un test exige que chaque skill citée soit déclarée, et elles servent quand une personne retire une skill par défaut) ; celle de `code-review` corrigée. `GLOSSARY-MAP.md` présent : la skill propose les termes dans le glossaire du contexte concerné qu'il liste, sans créer de carte. Étape « avant d'écrire » : lire aussi `CONTRIBUTING.md`, `CODING_STANDARDS.md` et un `REVIEW.md` existant, pour proposer un ajout plutôt qu'un doublon. `commands/spec.md` : retirer « Do not ask the user to run ai-kit init-workflow ». — Acceptance : tests de cohérence (exigence 12) ; `/spec` sous 4 000 caractères.
11. **Skills.** La skill lit les skills du dépôt (`.agents/skills/`, `.claude/skills/`, `.codex/skills/`, `.gemini/skills/` du dépôt) et les cite dans « Where the rest lives ». Elle ne cite jamais dans un fichier du projet une skill personnelle ni une skill du kit. Une règle d'une skill perso qui doit valoir pour le projet s'écrit dans l'`AGENTS.md` comme règle du projet. — Acceptance : test sur le texte ; le modèle `AGENTS.md` ne nomme aucune skill du kit.
12. **Proposée au bon moment, une fois.** `/review` : quand le dépôt n'a pas de `REVIEW.md` et que le changement est standard ou full, une ligne en fin de rapport propose `init-project-context`. `tdd` : quand l'`AGENTS.md` n'a pas de bloc « Verifying your work », une ligne propose la skill avant de deviner les commandes. Jamais comme prérequis, jamais deux fois dans la session. — Acceptance : tests sur le texte ; `commands/review.md` sous 4 000 caractères ; `commands/build.md` inchangé.
13. **Tests de contrat** (fichier `tests/test_project_context_contract.py`), sans modèle, en CI sur les 3 OS :
    - passes du modèle `REVIEW.md` = passes de `code-review` ;
    - vocabulaire des niveaux identique dans le contexte du kit, `/build`, `/intent` et les modèles ; aucun ancien libellé ;
    - chaque fichier cité par chemin relatif dans une skill du kit (`templates/…`, `references/…`, `*-FORMAT.md`) existe dans la skill citée ;
    - aucun nom retiré n'est cité hors CHANGELOG, ADR et résultats d'eval : `init-workflow`, `Security scan`, `.ai-kit/protected-paths` (liste tenue dans le test) ;
    - les titres que les commandes lisent dans un projet (« Verifying your work », « ## Report », « Things the agent gets wrong ») existent dans le modèle `AGENTS.md`.
    — Acceptance : le fichier passe sur le code livré, et chaque test casse quand on réintroduit l'écart qu'il garde (montré une fois à la main pendant le build).
14. **Evals** (deux cas, lancés seulement avec l'accord de la personne, 3 essais Codex chacun) :
    - initialisation d'un petit dépôt sans contexte (fixture) : la réponse propose un `AGENTS.md` avec la vraie commande de test du dépôt, un `REVIEW.md` qui ajoute aux passes du kit, aucune création de `CLAUDE.md`, aucune recopie (« Never commit », `docs/sdlc/`) ;
    - monorepo (fixture avec `apis/` et `apis/billing/` qui remplace la commande de test) : pour un changement dans `apis/billing`, l'agent annonce la commande de l'app, pas celle de la famille.
    — Acceptance : échantillons pass et fail vérifiés hors ligne par le runner ; résultats payants enregistrés dans `evals/results/` quand la personne les lance.
15. **Docs et versions.** ADR 0032 (proposed puis accepted) ; `docs/adr/README.md` ; CHANGELOG 4.10.0 ; `docs/commands.md` (init-project-context, monorepo) ; `docs/cli/claude-code.md` ; `docs/cli/matrice.md` (ligne « Repository context » : fichiers imbriqués par CLI, agy non vérifié) ; versions des skills modifiées incrémentées ; `VERSION` et `pyproject.toml` en 4.10.0. — Acceptance : suite complète verte, `test_doc_links` et `versions.py --check` verts.

## Constraints and policies applied
- Pas d'écriture sans une confirmation groupée ; jamais d'écrasement d'un fichier existant : ajout proposé (skill, inchangé).
- Budgets : contexte du kit < 3 800 caractères (3 778 aujourd'hui : la ligne `CLAUDE.md` réécrite ne doit pas grossir) ; commandes < 4 000 (`/build` intouché, `/review` et `/spec` vérifiés) ; détail du monorepo dans `references/monorepo.md`, chargé seulement pour un monorepo.
- Dépôt public et générique : exemples neutres (`ui/`, `apis/`, `apis/billing`), aucun nom de projet, d'entreprise, de personne ni de kit concurrent.
- Pas de rétrocompatibilité : pas d'alias ni de migration des anciens `REVIEW.md`.
- Ne jamais affaiblir un test : les tests existants qui assertent l'ancien texte sont mis à jour au nouveau contrat, nommés dans le rapport de build, chacun gardant une assertion du nouveau comportement.
- Evals facturées : avec accord ; Codex seulement, aucun essai sur agy sans accord.
- Pas de section Threats : le changement ne touche ni données personnelles, ni secrets, ni authentification, ni entrée externe ; il renforce la revue (Security ne peut plus être retirée).

## Areas of concern
- **Sens de `REVIEW.md` changé pour les projets existants** : un projet qui retirait volontairement une passe ne le peut plus ; il le verra dans les limites de la revue. Voulu (décision A). Décide : Hachem.
- **Contexte du kit à 22 caractères du plafond** : la ligne `CLAUDE.md` doit être réécrite à longueur égale ou plus courte. Si impossible, raccourcir une autre ligne ; jamais relever le budget. Décide : Hachem si une autre ligne doit bouger.
- **Allègement de l'`AGENTS.md`** : un collègue ou un agent en CI sans le kit ne voit plus « never weaken a test » ni la convention `docs/sdlc/`. Accepté dans la discussion (règles du kit, pas du projet) ; un projet qui veut les imposer à tous les écrit comme règles du projet.
- **Gemini CLI concatène tous les `AGENTS.md`** lancé à la racine : un monorepo à étages charge toutes les familles. Atténuation : fichiers courts, carte racine minimale, `.geminiignore` possible ; à mesurer seulement si un usage réel s'en plaint.
- **agy sur les fichiers imbriqués : non vérifié**, Codex vérifié seulement par sa doc (assumption) ; l'héritage explicite limite le risque, l'eval monorepo ne couvre que Codex.
- **Proposition par `tdd`** : la skill est chargée à l'étape 2 de `/build`, avant la vérification ; la proposition arrive donc un peu tôt, mais `/build` est à son budget. Alternative écartée : une ligne dans `/build`.

## Open questions
- Aucune question bloquante.
- Assumption : Codex lit les `AGENTS.md` de la racine jusqu'au dossier courant, le plus proche en dernier ; à vérifier dans sa doc pendant le build (lecture, gratuite).
- Assumption : agy lit les `AGENTS.md` imbriqués ; non vérifié ; un essai facturé au plus, avec accord.
- Le découpage en tâches se fait dans `/build` (plan.md) ; pas de tickets.
