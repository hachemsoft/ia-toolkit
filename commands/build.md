Activate the tdd skill for the tests of step 2, then the code-review skill on the whole change before step 3 (if a skill is not installed here, follow the instructions below directly). A cited ticket: fetch it and state its title first; an ambiguous reference: ask.

Stage: Build. Goal: an implementation that does what was asked, verified, with no more ceremony than the change needs.

Input: {{args}} (a ticket, a spec.md section, or a short description).

Choose the ceremony level (quick, standard or full, as defined in the kit context 00_KIT.md). A change to a function's return value, the type of error it raises or its parameters changes its contract: never quick, even on one line; a message's wording alone does not. The first line of your reply is `Level: quick`, `Level: standard` or `Level: full`, then a short reason; write it even if you then ask, stop or are blocked. A go-ahead the person already gave stands: do not ask for it again, except for the acceptance tests of step 2.

Step 1, plan, proportionate to the level. Quick: no plan file; say in one line what you change and how you check it, then step 2. Standard: a short alignment in the conversation (files, approach, proof); go on when the person agrees or already asked you to proceed; no plan.md unless asked. Full: read spec.md, intent.md, AGENTS.md and GLOSSARY.md when they exist; produce plan.md where the repo keeps such notes (AGENTS.md), otherwise in the change folder docs/sdlc/<date>-<slug>/ (created if needed; local, git-ignored by default), with: Files that change, Order of work, Risks first (how a failure would show and how to undo it, for an irreversible operation the backup or way back; or "not applicable"), Proof (the tests or checks proving each step). Without a repo convention, use init-project-context's templates/plan.md: titles in English, content in the user's language. Stress-test it: what could break, the riskiest step, rejected alternatives. Do not edit code until the person accepts the plan; use the CLI's plan mode if it has one.
Step 2, implement. Quick: no test written first; make the change, then the existing checks that cover it. Standard and full: before any code, write the acceptance tests, from the acceptance criteria of spec.md when there is one (a named manual check where no test can), else for the behaviour asked; at most three, else propose to split the change. Show them failing on their assertion, not on an import or compile error (an empty stub in a new file or a test-config change may get there; no other existing file changes before approval), with why it fails and what each asserts, then wait for the person to approve them (`review:` marks in the files: one open means not approved); only an explicit "do not stop for the tests" skips this, noted in the reply. With no test runner, show the playbook's check instead. A docs-only change or a pure refactor needs no new test. Once approved, the implementation is free (tdd's red-green loop when it helps); keep the tests as approved and never commit while it fails. Commit per slice only when the repo works that way and the person agreed to commits in this session (ask once). Domain playbooks: when an installed playbook (listed in 00_KIT.md) matches the files or the task, follow it, including its "In the kit commands" section for this step.
Step 3, verify, proportionate to the level: quick, the check that covers the change; standard and full, every check listed under "Verifying your work" in AGENTS.md for what changed. Paste the real output. Never report a check you did not run. Delegate the final verification to the ai-kit-verifier agent when available (else run its proof yourself) and relay its report; a test that passes without the code stops here: the person decides.
End with what changed, what was verified (its output), what remains. Report format: if the repo's AGENTS.md or the user's USER.md has a "## Report" section, shape the final report as it says (the repo's wins); otherwise use the default above. Retry limit: if the same check still fails after three different fixes, stop; report what you tried, the literal failing output and your suspicion, then ask.
