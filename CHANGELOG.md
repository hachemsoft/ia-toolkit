# Changelog

## 4.2.0 (2026-11-13)

Three new shell guardrails, off by default, and a count of what the guardrails refuse. Update the kit to install it: `ai-kit sync` with a Core repository, else a new ZIP or `git pull`, then its installer.

- **`git-guard`**: refuses `git reset --hard`, `git clean -f`, a checkout or restore of the whole tree, `git branch -D`, and a forced push or a deletion of `main` or `master` (more branches with `AI_KIT_PROTECTED_BRANCHES`).
- **`bq-cost-guard`**: refuses `bq query` without `--dry_run` and without `--maximum_bytes_billed`.
- **`infra-prod-guard`**: refuses `terraform apply` and `destroy` and the `kubectl` commands that change a cluster when the workspace, folder, variable file, context or namespace names production; `AI_KIT_ALLOW_PROD=1` allows it, as for dbt.
- **Turning one on**: `git-guard = true` under `[hooks]` in `aikit.toml`, then `ai-kit sync --offline`; IT can lock or set each one in `managed.toml`. They read the programs a command runs, so a command that only talks about an action passes (`echo "git reset --hard"`).
- **One hook for the shell guardrails**: `dbt-prod-guard` and the three new ones are rules of one script; each CLI gets one hook, `ai-kit-shell-guard`, instead of one per guardrail. The names in `aikit.toml` and `managed.toml` do not change. Files generated earlier by `ai-kit managed-settings` name the old script: generate them again.
- **Refusals counted**: each refusal adds a date and the guardrail's name to `~/.ai-kit/refusals.jsonl`, never the command; `ai-kit usage` prints `Guardrail refusals: …`.
- `ai-kit doctor` proves each guardrail turned on; a test holds each guardrail script under half a second per call.

## 4.1.1 (2026-11-12)

The `protected-paths` guardrail refuses plain forms it let through. Update the kit to install it: `ai-kit sync` with a Core repository, else a new ZIP or `git pull`, then its installer.

- **Configuration folders**: a command aimed at the folder itself is allowed only when every program only reads, so `find ~/.ai-kit -delete` and `find … -exec rm` are refused; so is the folder kept in a variable (`p=~/.ai-kit; echo x > $p/aikit.toml`), `sort -uo` on a protected file and `git -c key=value` next to one.
- **Kit commands**: `init`, `sync`, `rollback`, `uninstall` and the others are refused wherever their options are written (`ai-kit --home <folder> uninstall`) and through a launcher however it is run (`python3 scripts/launcher.py`, `./scripts/bootstrap.sh`, `cmd /c Installer.cmd`); a launcher of a kit folder with no action installs, and is refused too.
- **`.env`**: a shell command that writes `AI_KIT_*` or `DBT_TARGET` into a `.env` file is refused, as the write tools already were.
- **Protected files**: the news the session hook shows (`~/.ai-kit/news/`, `news.json`) and agy's own permissions file join the list.
- Reading stays allowed: `ls`, `du`, `cat`, `find` without an action, `git -C <folder> status`, `ai-kit status`.

## 4.1.0 (2026-11-10)

**Breaking for MCP definitions**: a server definition that an earlier version only reported is now refused, and the change stops until its source is fixed.

- **MCP** (ADR 0022): a key outside the closed list, a shell or a shell script as the command, and a value that looks secret in `args` (`--token value`, `--token=value`, a known token format) or in the URL (a password, `?api_key=`) are refused; write `${VARIABLE}`.
- **`managed-settings` for Windows**: a `windows/` folder with Claude Code's managed settings, whose guardrails run through PowerShell with the venv's `Scripts\python.exe`. Gemini CLI does not document its hook shell on Windows: its Windows file only turns YOLO mode off.
- **Writes**: SIGTERM and SIGHUP during an installation put every file back, as Ctrl+C does; "modified locally" errors say how to proceed.
- **Guardrail `protected-paths`**: `sed` and `awk` no longer count as readers of a protected file (their scripts can write or run a command); read with `cat`, `grep`, `head`.
- **Launcher**: an environment that starts is never deleted; `status`, `doctor`, `usage` and `validate` run without pip; `Installer.cmd` falls back to the kit's own environment when no Python is on the PATH; the `ai-kit` command works from a folder with non-ASCII characters on Windows; a refused registry change is reported instead of failing.
- `uninstall` with nothing installed exits with 0, so `uninstall --remove-runtime` still removes the runtime.
- The installation summary lists each guardrail on or off; `USER.md` no longer holds your email; `doctor` says when a CLI's version is unreadable and when the `ai-kit` command is not executable.
- Commands: `/diagnose` proposes a mitigation first when users are hurt now; `/build` lets a docs-only change or a pure refactor prove itself with the existing checks; `intent.md` has a Status line.
- Licences: the Summary section of `mr` adapts HumanLayer's `show-me` skill; its Apache License 2.0 now ships (`skills/LICENSE-HUMANLAYER-APACHE-2.0`). The build backend is pinned; Dependabot also watches the Python dependencies.
- Eval cases can carry sample answers that an offline test checks against their criteria.
- Cleanup: no migration code from earlier installations, no profile left in the engine, `aikit-tier` removed (`aikit-default` decides), ADRs state the decisions as implemented, CHANGELOG headings carry their date.

## 4.0.0 (2026-11-09)
The final V2 design, without any compatibility layer for earlier versions. **Breaking**: reinstall from the 4.0.0 ZIP; older settings files are not read.

- **One command line**: `init`, `sync` (`--offline` re-applies, `--from-bundle`), `team list|use`, `status`, `doctor`, `rollback`, `user edit`, `uninstall`, `usage`, `friction`, `managed-settings`, `validate`. `setup`, `update`, `news`, `new` and the guided installer are gone; the launchers run `init` when no action is given. Exit codes: 1 refused or failed, 2 usage error, 3 `managed.toml` unusable.
- **One personal file**: `~/.ai-kit/aikit.toml` (`[user]`, `[hooks]`, `[mcp] enabled/denied`, `[frictions]`, `[core]`, `[teams.<name>]`); `overrides.toml` is not read. The personal context is `USER.md`.
- **No organization file**: the Core defines its MCP servers in `mcp/servers.toml`; IT sets locked guardrails and the friction tracker in `managed.toml`; teams are Team repositories.
- **Team MCP servers** (ADR 0022): a Team may ship `mcp/servers.toml`. A local server it brings runs only when IT lists its exact identity (`mcp.allowed_stdio`) or you approve it once in a terminal; an unpinned `npx`/`uvx` launcher is refused; a `required` server that cannot run stops the change.
- **Signed tags** (optional): with `git.signers` in `managed.toml`, a Core or Team tag must carry an SSH signature from one of the listed keys.
- **What's new** is read from the installed copies of `CHANGELOG.md` and `NEWS.md` (`~/.ai-kit/news/`), never from the network.
- `sync`, `team use` and `rollback` no longer ask your identity again; only `init` does.
- An invalid `[frictions.tracker]` in `managed.toml` exits with code 3, like any unusable managed setting.
- Documentation rewritten and shortened, with architecture diagrams; the V2 decisions (ADR 0013 to 0026) are published in `docs/adr/`.
- Removed: the friction `--mode` option (set `[frictions] capture` in `aikit.toml`), skill and guardrail aliases, legacy folder and settings migrations.

## 3.0.0 (2026-11-09)
The V2 structure, complete. **Breaking**: no more profiles (`--profile <job>` is refused; `general` is still accepted), the installed package holds only the engine (the release ZIP ships the Core as `core/ai-kit-core.bundle`), `organization.toml` leaves the Core, and `practices/` is `context/`. An installation made with a profile keeps everything it had (its resources become personal lines, commented, at the next update); an organization's own Core with `organization.toml` or `practices/` is still read. This Core needs AI Kit 3.0 or newer (`min_engine`): an older engine refuses it and changes nothing. Git 2.29 or newer.

- MCP policy (V2 slice 6): a server's keys are a closed list (`command`, `args`, `env`, `cwd`, `httpUrl`, `url`, `headers`, `required`), and a shell as the command or a `-c` script is reported; both are warnings in this release and will be refused in a later one. IT can allow only exact server identities (`managed.toml` `mcp.allowed_stdio`, `mcp.allowed_http`: the hash of the command, args, env templates and folder, or of the URL and headers; `ai-kit status --verbose` shows them), and `mcp.denied` now matches a name, a URL prefix or an executable. A server refused by IT and marked `required = true` stops the installation; an optional one is removed with a notice; `required` is never written into a CLI.
- `managed-settings` also applies `managed.toml`: its locked guardrails and its MCP refusals go into the files IT deploys.
- `state.json` records where each installed skill and agent comes from (package, Core, or Team).
- The session hook no longer puts any remote text in the agent's context: from the daily remote read, only the remote `VERSION` (checked `X.Y.Z`) is used; announcements come from the installed `NEWS.md`.
- Frictions (V2 slice 7, ADR 0023): local entries older than 30 days are purged (`managed.toml` `frictions.retention_days`), at session start and by `status`; the same friction told several times is one issue with its count; emails, home paths and internal host names are redacted before a friction is stored; with approval, the agent says at session start how many frictions wait, and never sends them.
- `ai-kit user edit` opens your personal context in your editor (its path when there is no terminal).
- `/me` reads only a bounded list of local facts; `/retro` proposes changes to the current repository only, and turns what concerns the kit, a Core or a Team into a friction.
- `skills/catalog.json` and `agents/catalog.json` are gone (V2 slice 8): each skill and agent describes itself in its front matter (`aikit-*` metadata), which `ai-kit new` now writes.
- Analysis (ADR 0026): `/explain` also answers a question about the project with evidence, through the new `analysis` skill (frame, explore, verify each claim, report verdict, evidence and unknowns); `/research` and its `investigation` skill join the general selection.
- `scripts/export_core.py` writes the kit's content as a Core repository in its V2 layout (skills and agents flattened, manifest `kind = "core"`, a Git repository tagged `v<version>` with `--git`; nothing pushed); `examples/team-repo/` is a Team repository to copy; `ai-kit validate --path` checks both (a Team may not hold commands, policies, hooks or profiles).
- `ai-kit sync --from-bundle <file>` installs the Core from a `git bundle` without network, with the same tag checks, recorded under the configured Core URL.
- **The package holds only the engine** (code, runtime scripts, schemas, templates); the release ZIP ships the content as a Core, `core/ai-kit-core.bundle`, a git bundle of this repository at the version's tag (this repository is the Core). The first installation activates it offline, without a question (the package is the trust anchor), under IT's `enterprise.core`, the person's `[core] repo`, or this repository's URL; `lock.toml` and the source cache keep it, so the extracted folder can still be deleted. Run from a clone, the kit reads the clone's content as before. Git 2.29 or newer is needed (fetches no longer record their origin).
- **No more profiles** (V2 slice 9, ADR 0018): the Core installs its default selection for everyone (each skill, agent and command says it with `aikit-default`, or `default: false` for a command); a Team turns on more, and a person adds or removes a resource with `extra_*` and `disabled_*`. `--profile general` is still accepted, any other profile is refused with how to get its resources; the guided installer no longer asks for a profile; `ai-kit new profile` is gone; the context and the summaries no longer name a profile; a friction records the team instead.
- An installation made with a profile keeps everything it had: at its next update, what the Core default does not give is written as personal lines (`extra_skills`, `extra_agents`, `extra_commands`, and `[mcp] <name> = true` for the servers the profile turned on), with a comment `# carried over from profile <name> on <date>`, once; the person is told. Nothing expires on its own.
- `docs/getting-started.md` shows what the Core installs by default and what is optional, instead of the profile table.
- `practices/` is now `context/` (the company and team layers of the context); a Core that still has `practices/` is read the same way.
- `organization.toml` leaves the Core: IT sets the friction tracker in `managed.toml` `[frictions.tracker]` (and the locked guardrails in `hooks.locked`), the Core defines its MCP servers in `mcp/servers.toml`, each team is a Team repository. An `organization.toml` still present in an organization's copy of the Core is read as before, and `ai-kit validate` says where each key goes. `SECURITY.md` now covers `managed.toml`, Git sources and MCP validation.

## 2.1.0 (2026-11-08)
Core and Team content from Git, at stable tags, with rollback. Without a Core or Team source configured, nothing changes.

- Core source from Git (V2 slice 2): `ai-kit sync` installs the highest stable `vX.Y.Z` tag of the Core repository set by IT (`managed.toml` `enterprise.core`) or by the person (`aikit.toml` `[core] repo`), never a branch; `ai-kit rollback` goes back to the previous Core, without network, and a second rollback comes back. `~/.ai-kit/lock.toml` records the URL, tag, tag object, commit and tree digest, written in the same transaction as the files; `update` keeps the locked Core. Without a Core source, nothing changes.
- Git runs from one module with an allowlisted environment, no global or system config, explicit `-c` overrides and a credential helper from a closed list; URLs are canonicalised (https and ssh only, no credentials, no `..`), checked against `git.allowed_hosts` and `git.allowed_groups`, and must not be rewritten. A tag seen once that moves blocks (`tag-moved`); `git.revoked` commits are never activated. Trees are read with `ls-tree`/`cat-file`: symbolic links, submodules, `.git`, Windows reserved names and case collisions are refused. The first use of an origin outside managed mode asks for confirmation in a terminal.
- An activation cut by a power loss is put back at the next start (backup manifest `pending`/`done`); one command changes files at a time (`~/.ai-kit/engine.lock`).
- `doctor` shows the active Core and whether `lock.toml` was edited. The agent may not run `sync` or `rollback`, nor write `lock.toml` or the source cache.
- Resources describe themselves (V2 slice 3): each `SKILL.md` and agent file carries its `aikit-*` metadata (version, origin, summary, category, tier, requires, one `aikit-optional-<skill>` per optional skill); the engine rebuilds the catalogs from the files and no longer reads `skills/catalog.json` or `agents/catalog.json` (kept until a later release; a test checks they agree). The metadata is removed from the installed files, so every CLI receives the same files as before (the `mr` credit is now one line). Front matter is read by a dependency-free parser (scalars, lists, one-level tables). A required skill that does not exist, or a cycle, is refused.
- `ai-kit validate [--path FOLDER]` checks a content tree before it is tagged: manifest, metadata, names, requirements and cycles, commands' skills, check_skills.
- `doctor` says, for each CLI installed, which kit capabilities work natively, which are degraded and which are blocked, and why (V2 slice 4). The adapters no longer receive the profile: they work from the resolved selection; the installed files are unchanged.
- Teams from Git (V2 slice 5): `ai-kit team use <name> [--url URL]`, `team use none`, `team list`. The active Team adds its skills and agents on top of the Core (never replacing a protected one, never bringing commands, policies or hooks), turns on the resources of its `[defaults]`, and its `context/` becomes the team layer of the context. A known Team is activated from the cache without network; `sync` updates it; `rollback` restores the previous Core and Team. IT restricts Teams with `managed.toml` `[teams] allowed` and `allow_unknown`.
- `ai-kit status [--verbose]`: active Core and Team, rollback target, CLIs, IT keys; with `--verbose`, where each setting comes from, installed resources, capabilities. No network.
- `ai-kit init`: first installation (the general selection when no profile is given), then a first `sync` when a Core source is set.
- Fixed: with a Core synced, the guided installer and the re-apply after `/me` now use the locked Core instead of the package content.

## 2.0.0 (2026-11-08)
The first release of the V2 structure. **Breaking: Python 3.11 or newer** (the kit needed 3.9): a workstation on Python 3.9 or 3.10 stays on AI Kit 0.52, which keeps receiving security fixes; the launchers say what to ask IT.

- `managed.toml`, the settings IT imposes on AI Kit, read from a fixed administered path (macOS `/Library/Application Support/ai-kit/`, Windows `C:\ProgramData\ai-kit\`, Linux `/etc/ai-kit/`), never from an environment variable. Closed schema: every key present wins over the organization, the team and the person, whatever its value (`false` and `[]` included); a key absent locks nothing; `hooks.locked` and `mcp.denied` add to the other layers' restrictions; an unknown key, an unreadable file or a file the person could change refuses every change (exit code 3). Keys of this version: guardrails (switch and lock), `mcp.allow_stdio`, `mcp.denied`, `frictions.capture`, `frictions.publication`. `doctor` shows what it sets. Contract: `docs/managed.md`.
- Frictions are published with the person's approval by default: with a tracker set, an agent friction is no longer sent on its own; the person sends it from a terminal with `ai-kit friction --sync`, which the agent may not run. `frictions.publication = "auto"` in `managed.toml` restores sending at once; a person who refused sharing keeps their frictions local in every case.
- `doctor` says where each setting comes from (organization, team, you, IT) and when IT added, changed or removed `managed.toml` since the last update (its digest is recorded in `state.json`).
- `~/.ai-kit/aikit.toml`, the person's AI Kit 2 settings (`[user]`, `[hooks]`, `[mcp]`, `[frictions]`); `overrides.toml` keeps working through an adapter until then. `ai-kit update --migrate-config` writes it from `overrides.toml`, says where each setting went, and leaves `overrides.toml` untouched for a return to 0.52 (it is then no longer read). The person can only restrict the friction publication (`approval` or `disabled`).
- The content declares itself (`aikit.toml` at the kit's root: `name`, `min_engine`); an engine older than `min_engine` refuses it and changes nothing.
- JSON schemas for `managed.toml`, `aikit.toml` and the content manifest (`schemas/`), for editor completion; a test keeps them in line with the loaders.
- The engine and the content are read from two roots: the content (skills, agents, commands, practices, profiles, `organization.toml`) can come from another tree, the step before Core sources at a locked Git tag. Nothing changes for an installation (same files, checked by the golden snapshot).
- An organization lock (`locked_hooks`) binds the team and the person, not IT: a guardrail `managed.toml` turns off is not forced back on.
- TOML is read with the standard `tomllib`: the `tomli` dependency is gone. CI tests Python 3.11, 3.12, 3.13 and 3.14 on Linux, macOS and Windows.
- `setup`, `update` and `uninstall` refuse a `~/.ai-kit/state.json` written by a newer kit (its `schema_version` is higher than this kit understands, or malformed) and change nothing; until now the field was written and never read. A state without the field is migrated as before.
- `installer/cli.py` is split: the `ai-kit` command on the PATH and `uninstall` move to `installer/lifecycle.py`, unchanged (797 lines → 653, under the 800-line rule).
- `scripts/baseline_v1.py` freezes a model-free baseline of a release (tests, golden, inventory, selection of every profile, eval preconditions per CLI), the reference the V2 migration is compared with.
